
### 2.2.3 Chỗ query trực tiếp `user_roles` KHÔNG qua `has_role()` (frontend)

3 chỗ, đầy đủ:

| File | Dòng | Mục đích |
|---|---|---|
| `src/hooks/useUserDirectory.ts` | 175–182 | gate hiển thị email trong danh bạ user |
| `src/components/feed/ClaimHistoryModal.tsx` | 45–52 | gate xem toàn bộ lịch sử claim |
| `src/components/feed/FacebookCreatePost.tsx` | 425–432 | gate `isElevatedMediaAccount` (limit upload cao hơn) |

Cả 3 đều dùng pattern `.from('user_roles').select('role').eq('user_id', userId).eq('role','admin').maybeSingle()`.

Đánh giá:
- **Nguồn dữ liệu đúng** (bảng `user_roles`, không phải `profiles`) → không có rủi ro role cũ/lệch.
- **Rủi ro RLS recursion: không xảy ra** trong 3 ca này, vì policy trên `user_roles` là self-read đơn giản (`user_id = auth.uid()`), không tham chiếu lại bảng khác.
- Rủi ro còn lại là **P3 (nhất quán + cache)**: 3 chỗ này tạo 3 query riêng, không dùng cache 10 phút của `useAdminRole`, và bỏ qua mọi role khác ngoài `'admin'`. Chuẩn hoá về `useAdminRole` là dọn nợ kỹ thuật, không phải vá bảo mật.
- Cả 3 đều là **gate hiển thị phía client**; dữ liệu thật vẫn do RLS/RPC chặn.

Edge functions: ~70 function query `user_roles` trực tiếp bằng service-role client (không qua `has_role`). Đây là **service-role context, RLS không áp dụng**, nên không có rủi ro recursion; nhóm mới hơn (`admin-sql`, `admin-secrets`, `treasury-*`, `connector-admin-revert`, …) đã dùng `admin.rpc('has_role', …)`. Sự chia đôi này là nợ nhất quán (P3), không phải lỗ hổng.

**Kết luận 2.2: PASS, không có phát hiện P0/P1.**

## 2.3 — SECURITY DEFINER functions

### 2.3.1 Tổng quan (raw query)

```sql
select count(*) from pg_proc p join pg_namespace n on n.oid=p.pronamespace
where n.nspname='public' and p.prosecdef;                                  -- 239

select count(*) from pg_proc p join pg_namespace n on n.oid=p.pronamespace
where n.nspname='public' and p.prosecdef
  and not exists (select 1 from unnest(coalesce(p.proconfig,'{}')) c
                  where c like 'search_path=%');                            -- 0
```

| Chỉ số | Số thật |
|---|---|
| Tổng function `SECURITY DEFINER` trong `public` | **239** |
| Thiếu `SET search_path` | **0** |
| Là trigger function (`returns trigger`) | 63 |
| Không có EXECUTE cho `anon` lẫn `authenticated` | 11 |
| Chỉ `authenticated` | 3 |
| `anon` + `authenticated` gọi được, không phải trigger | 162 |

**→ Rủi ro `search_path` injection: KHÔNG TỒN TẠI. 239/239 function đều pin `search_path`** (`public`, một số thêm `pg_temp`/`cron`/`extensions`). Đây là điểm mạnh của codebase.

11 function **đã khoá đúng** (không grant cho anon/authenticated — chỉ service-role gọi được): `admin_sql_exec`, `app_secret_get/set/delete`, `apply_attester_signature`, `find_similar_profiles_for_impersonation`, `fp_backfill_eligible_count/eligible_profiles/lookup_one`, `fun_profile_outbox_publisher_claim/ack`.

3 function chỉ `authenticated`: `connector_revert_link`, `get_my_profile_private`, `tokens_registry_coverage_30d`.

Query dùng để phân loại (đầy đủ, không lấy mẫu):

```sql
select p.proname||'('||pg_get_function_identity_arguments(p.oid)||')',
  has_function_privilege('anon', p.oid, 'EXECUTE'),
  has_function_privilege('authenticated', p.oid, 'EXECUTE'),
  p.prorettype::regtype::text,
  position('auth.uid' in pg_get_functiondef(p.oid))>0,
  position('has_role'  in pg_get_functiondef(p.oid))>0,
  array_to_string(p.proconfig,',')
from pg_proc p join pg_namespace n on n.oid=p.pronamespace
where n.nspname='public' and p.prosecdef order by 1;
```

Kết quả: **93 function** gọi được bởi `anon`/`authenticated`, không phải trigger, và **thân function không chứa `auth.uid()`, `has_role()`, `current_user`, `session_user` hay `current_setting`** — tức **không có bất kỳ kiểm tra quyền nào bên trong**. 72 function còn lại có kiểm tra `auth.uid()`/`has_role()` nội bộ.

### 2.3.4 Nguyên nhân gốc chung

Không phải 93 lỗi độc lập. Là **một mẫu thiết kế**: hàm được viết cho edge function service-role gọi, nhưng `GRANT EXECUTE` mặc định của Postgres (`PUBLIC`) chưa bị `REVOKE`, nên `anon`/`authenticated` thừa hưởng. Cùng loại vấn đề với "grant pollution" đã ghi ở 2.1 (§anon giữ SIUD trên ~250 bảng) — chỉ khác là ở tầng bảng có RLS đỡ, còn ở tầng function `SECURITY DEFINER` thì **RLS bị bỏ qua theo định nghĩa**, nên không có lưới an toàn thứ hai.

### 2.3.5 Mục CHƯA CHẠY (ghi rõ để không nhận nhầm là đã verify)

1. Đọc **toàn văn** thân 93 function (lượt này đọc đầy đủ 8 function rủi ro nhất, còn lại phân loại bằng tín hiệu tĩnh: grant + vắng mặt mọi guard + chữ ký tham số).
2. Truy vết caller thật của từng function (FE / edge / cron) để biết cái nào `REVOKE` được ngay mà không vỡ tính năng.
3. `SECURITY DEFINER` **VIEW** (`security_invoker=false`) — chưa quét, cũng là mục tồn từ 2.1.
4. Guard cuối trên đường ghi `profiles.wallet_address` (`fn_wallet_writer_guard`, `enforce_wallet_kill_switch`) khi đi qua `process_wallet_change`.
