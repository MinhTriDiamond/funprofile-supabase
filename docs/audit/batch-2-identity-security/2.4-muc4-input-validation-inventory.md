# Mục 4 — Kiểm kê input 5 function tài chính/danh tính (2026-08-16, LIỆT KÊ, CHƯA SỬA)

Trạng thái: chỉ liệt kê theo yêu cầu. Không sửa code trong đợt này.

## 1. `claim-reward` — P1

```ts
// supabase/functions/claim-reward/index.ts:80
const { wallet_address, amount } = await req.json();
if (!wallet_address || !amount) { /* 400 */ }
const claimAmount = Number(amount);
```

Thiếu:
- `wallet_address`: không regex `^0x[0-9a-fA-F]{40}$`, không lowercase trước khi so sánh/lưu.
- `amount`: `Number()` ⇒ mất precision + chấp nhận `NaN`/`Infinity`/số âm/chuỗi khoa học (`1e21`). Không chặn `<= 0`, không chặn số thập phân vượt decimals.
- Không giới hạn độ dài body.

Đề xuất (đợt sau): Zod `{ wallet_address: z.string().trim().regex(EVM_ADDR).transform(s => s.toLowerCase()), amount: z.string().regex(/^\d+(\.\d{1,18})?$/) }`, tính bằng BigInt string theo rule 6.

## 2. `record-swap` — P2

```ts
// supabase/functions/record-swap/index.ts:34-46
const body = (await req.json()) as Body;
const fromAmount = Number(body.from_amount);
const toAmount = Number(body.to_amount);
if (!(fromAmount > 0) || !(toAmount > 0)) return json({ error: 'invalid_amount' }, 400);
```

Có `requireUser` + chặn `<= 0`/`NaN` (nhờ `!(x > 0)`), nhưng:
- Vẫn `Number()` ⇒ precision (ghi vào `swap_transactions.from_amount/to_amount`).
- `from_amount_usd` / `to_amount_usd` nhận thẳng từ client, không validate dải giá trị ⇒ có thể bơm USD ảo vào thống kê.
- `tx_hash`, `token_symbol`, `chain_id` (nếu có trong Body) chưa regex/whitelist.

Function đã `@deprecated`, trả **410 Gone** ngay sau OPTIONS, không đọc body, không chạm DB. ⇒ Gạch khỏi danh sách mục 4.

## 4. `delete-user-account` — cần CTO duyệt riêng (không chỉ là thêm validate)

Luồng hiện tại (`supabase/functions/delete-user-account/index.ts`):
1. Yêu cầu `Authorization` header, `userClient.auth.getUser()` ⇒ chỉ tự xoá chính mình (không nhận `user_id` từ client) ✅.
2. Sau đó dùng `adminClient` (service key) xoá tuần tự ~40 bảng theo `user_id`, rồi xoá auth user.

Rủi ro thực tế **không phải input validation** mà là:
- **Không có bước xác nhận chủ ý** (không yêu cầu nhập lại username/mật khẩu/OTP) ⇒ 1 request là mất tài khoản vĩnh viễn.
- Không đọc body ⇒ không có gì để validate.
- Xoá cứng, không soft-delete/không snapshot ⇒ không thể hoàn tác; dữ liệu tài chính (`donations`, `transactions`, `mint_allocations`) nếu bị xoá theo sẽ làm lệch đối soát.

⇒ **Đề xuất tách đề xuất riêng cho CTO**: thêm bước xác nhận (nhập chính xác username, hoặc OTP email), chuyển sang soft-delete + hàng chờ 30 ngày, và giữ lại bản ghi tài chính (ẩn danh hoá thay vì xoá). Lovable **không** tự sửa.

## 5. `identity-dispute-submit` / `identity-dispute-resolve` — P2

```ts
// identity-dispute-submit/index.ts:22
const { dispute_type, target_ref, reason, evidence = {} } = await req.json();
// identity-dispute-resolve/index.ts:27
const { dispute_id, decision, resolution_note = '' } = await req.json();
```

Thiếu:
- `dispute_type` không whitelist theo enum `dispute_type` (6 giá trị), `decision` không whitelist (`accepted|rejected`).
- `reason` / `resolution_note` không giới hạn độ dài ⇒ có thể nhồi text lớn.
- `dispute_id` không validate UUID.
- `evidence` là JSON tự do, không giới hạn kích thước/khoá.
